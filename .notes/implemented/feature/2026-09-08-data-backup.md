# Agent Note: 用户数据备份与删除保护

Status: implemented

## Problem

笔记数据库、项目和产物分别持久化，直接复制正在写入的文件难以建立可用的恢复点。项目与产物的永久删除缺少独立副本，而日常使用数据所在目录的名称容易被误认为可随意清理的开发数据。

## Decision

[备份工具](../../../packages/storage-backup/src/index.ts)是供本地 Provider 和运维命令使用的纯存储库，不发布 Cordis 服务，也不改变 Feature 对 Capability 的依赖方向。完整目录快照与删除恢复记录共享版本化清单、SHA-256、私有权限、刷盘和发布前校验。完整备份提供恢复到新目录的命令，避免恢复操作覆盖当前数据。

启动器在持有数据锁时先创建完整快照，再启动固定构建。Provider 在各自删除或解除归属的写入边界保存原始记录；SQLite 的恢复记录写入失败使事务回滚。锁不猜测其他 DSH 进程的状态，崩溃后保留锁并要求人工检查。范围、命令和限制由[备份指南](../../../docs/backup.md)承载。

开发 Profile 刷新只在缺少用户补丁文件时创建默认值，保留现有配置，避免准备运行环境时重置日常使用设置。

SQLite 在只读打开干净关闭的 WAL 数据库时也会创建空 WAL 和 SHM。快照验证忽略新建的零字节 WAL 与 SHM，继续比较所有已有 WAL、非空 WAL 和数据库主体；重复备份与恢复测试覆盖桌面二次启动遇到的这个边界。

## Alternatives considered

只增加规则和手动复制说明：不能约束 Provider 的实际删除行为，也不能检验 SQLite WAL 数据是否完整，因此不足以保护用户内容。

每次删除都复制整个目录：会使一次回收站操作的耗时随视频资料总量增长。选择操作前原始记录，并在启动前和手动命令中提供完整快照。

直接恢复覆盖当前目录：可能丢失备份之后的新内容，并混入旧数据库旁文件。恢复到新目录可以先检查结果，再保留并切换原数据目录。

## Consequences

删除与启动会增加备份 I/O；磁盘不足或备份路径不可写时操作停止。恢复记录不提供自动合并，项目与笔记的跨文件删除也不成为分布式事务。备份不自动清理，需要使用者管理空间。

[契约测试](../../../tests/contract/backup.test.ts)验证 WAL、恢复后重新挂载 Provider、FTS、回收站、元数据、二进制内容、失败时保留原内容、路径与完整性校验。[命令测试](../../../tests/integration/data-backup.test.ts)验证独立进程中的创建、校验、恢复和互斥。[运行模式验收](../../../tests/e2e/dev-modes.test.ts)检查启动前备份和退出释放锁；包安装门禁覆盖独立安装中的删除路径及共享库依赖。
