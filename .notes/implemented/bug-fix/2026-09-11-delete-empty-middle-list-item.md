# Agent Note: 删除空的中间列表项时保持列表连续

Status: implemented

## Problem

在 `aaa / bbb / ccc` 三项有序列表中，清空 `bbb` 后再次退格，会留下空段落并把 `ccc` 分隔为重新从 1 编号的另一段列表。用户要移除这一项，却必须继续修复列表结构。

已安装的 TipTap 3.31.3 的 `ListKeymap` 在列表项首段开头退格时调用 `liftListItem`；中间项被提升到列表外，前后列表随之分开。真实浏览器回归用例在修复前断言失败：删除空项后出现两个 `ol`。这与[空项解析补齐](2026-09-11-empty-ordered-list-item.md)是不同入口的问题，后者负责 Markdown 重载时的文档合法性。

## Decision

[删除扩展](../../../packages/ui-notes/src/client/lib/delete-empty-list-item.ts)通过 TipTap 的公开快捷键接口处理退格和向前删除，优先级 110 高于安装版本的列表键盘处理及分支删除扩展（101）。注册与清理由编辑器生命周期管理，不涉及 DSH 接口或上游源码修改。

仅当选区为光标、当前段落为空、所在列表项只有该段落，且同层列表中前后均有兄弟项时，事务直接删除整个空项。列表容器、起始序号、相邻项内容和属性保留，光标移到后一项开头。规则适用于有序、无序和待办列表，也适用于嵌套列表的当前层。文本选区、首尾项、单项列表和仍含其他块的列表项交由默认处理。

删除事务通过公开的历史接口与此前清空文字的操作分组，撤销可先恢复空项，再恢复被清空的文字。当前交互约定见 [UI 规范](../../../docs/ui-packages.md)。

## Alternatives considered

在每次事务后自动清理空项：会吞掉按回车新建的合法空列表项，并影响 Markdown 重载，无法区分用户继续输入与明确删除的意图。

全局替换列表退格逻辑或修改 TipTap 安装包：扩大首尾项、嵌套项和非空项的行为变化范围；安装包修改也违反仓库规则。局部快捷键在不匹配时返回未处理，复用默认行为。

## Validation

[契约测试](../../../tests/contract/notes-list-deletion.test.ts)覆盖三类列表、非默认起始序号、相邻项的格式与子列表、待办状态、嵌套层级、光标与撤销重做，以及不应拦截的边界。[浏览器测试](../../../tests/e2e/notes-list-deletion.test.ts)通过真实键盘分别执行退格与向前删除，检查列表连续、撤销重做及自动保存后的切换重开。

## Consequences

移除中间空项只需一次删除操作，序号由同一列表容器自然递补。单独的空段落或历史编辑产生的分离列表不会被自动合并，保留文档中有意设置的列表分隔。
